# PrimeOps

Offline-first Android lighting survey app built with Capacitor 6. Each project requires a building name and inspector name and contains separately named inspection entries. Readings, notes, and photos are kept with their entry in on-device storage.

Client sign-in uses **Client code or company name**, **Username**, and **Password**, followed by **Sign in**. No separate company-switch action is needed. Company names must match an existing company (case-insensitive); duplicate names require the unique client code. Changing clients opens that client's existing isolated storage without copying or deleting another client's work. Passwords are never stored as part of the company handoff. Offline sign-in still requires a previously downloaded licence and account; company-name lookup works offline after a successful lookup on that server.

## PrimeOps release and migration

PrimeOps is the independent product name across the server, Windows field app, Windows owner console, Android app, installer filenames and reports. Existing client identities, users, passwords, buildings, checklists and records remain unchanged. Compatibility identifiers live in `www/legacy-identifiers.json`; they are internal migration inputs, not product branding. Do not delete the database, reset accounts or change `JWT_SECRET` during deployment.

The original PO mark is shared by sign-in, reports, Android launcher icons and Windows apps. Windows packaging embeds `desktop/icon.ico` and neutral product metadata into both executables through `scripts/brand_windows.cjs`; the source mark is `www/primeops-mark.svg`.

- Replace the server code while retaining the existing database, `.env`, report folders and Docker project/volume names. Set `POSTGRES_USER` and `POSTGRES_DB` to the existing database identities before deploying the new Compose file; Windows startup preserves legacy values automatically when those fields are missing. New installations default to `primeops`. The company registry is renamed in place; old session issuers, licences and encrypted signing keys remain readable.
- Existing browser data is copied into PrimeOps storage on the same origin; the original remains untouched. Keep the same server address. The Windows field app copies its existing profile and retains its origin for compatibility; new installs use a neutral origin.
- Android now uses `app.primeops.mobile` and installs alongside the previous app. It cannot access the old package's private data automatically. First install the **PrimeOps Migration** compatibility APK over the old app (same signing key/package). In that app choose **Home > Device backup > Move device data**, or **Move device data** on sign-in, and export an encrypted backup using a password of at least 12 characters.
- Install the new PrimeOps APK. Choose the same company before signing in, use **Move device data** to restore the file/password, then sign in and verify projects and **Pending changes**. Repeat per company if needed. Keep the old app and backup until every record and pending upload is verified. Already-synced server records remain available with the same usernames/passwords.
- Transfer includes credentials and offline jobs, encrypted with PBKDF2-SHA256/AES-GCM. Keep backups private. Restore refuses to replace existing local projects or pending work; it does not merge unrelated devices. Native installation and real-device migration still require an on-device check.

### Plans and feature activation

**Home > Subscribe** offers Basic (**R450/month**, 5-10 users, maximum 10), Building Managers (**R850/month**, 11-20 users, maximum 20), and Operations (**R1,500/month**, unlimited). Prices are final ZAR totals, VAT-inclusive where applicable. There is no minimum account count; every active account, including administrators, counts. Requests go to **PrimeOps Owner > Subscriptions**. Only owner approval changes the plan and future unissued subscription fees; issued invoices do not change and there is no mid-month adjustment. Creation/reactivation is checked transactionally, including offline uploads; over-limit work remains blocked for review, not silently discarded. Downgrades below current usage are refused. Existing clients retain their plan; new registrations default to Basic and the owner may choose another plan.

**Home > Features** lists every feature in `www/feature-catalog.json`. Company administrators select 1-5 free initial features and request owner approval in **PrimeOps Owner > Features**. Later additions show **R100 per feature once-off, testing only**. On a fee-bearing pending request, client administrators can simulate a full, partial or declined result; the outcome is clearly marked simulated and neither collects nor records real money. Simulation never replaces owner approval. Only the owner activates features. Later additions may exceed five as the product catalogue grows. New features added to that catalogue appear for existing clients but are not automatically enabled. User management, Home and Account remain essential and are not charged features. Existing clients retain their current features. Company entitlements intersect account permissions in both API and offline navigation.

**Home** shows a picture-labelled navigation card for every section available to the signed-in account, matching the navigation's permissions. Distinct offline SVG pictures (light bulb, checklist, repair tool, washing machine, receipt, people and folder) appear on both Home cards and main navigation buttons; text labels remain for clarity and screen readers. Cards use a compact two-column grid on phones, without horizontal scrolling. Phone users can open **Sections** to see a picture-labelled menu; it closes when a section is chosen, leaving room for the task. **Home** and **Back** remain available. Inspection totals and quick actions are collapsed under **Inspection summary & quick actions**, rather than crowding the navigation.

Busy sections show one task panel at a time:
- **Users:** Find users / Add a user / Add a building. Account forms split details, building/section access and password/status.
- **Billing:** Overview / Transactions; managers also have Add transaction / Account status.
- **Lighting:** Measure / Entries / Readings / Photos / Reports, with the selected inspection entry always visible.
- **Building checks:** Start a check / Saved checks; monthly forms separate inspection details, questions and submitted reports. Individual check details separate photos, report revisions and history.
- **Tickets:** Active / Archive remain separate; expanded tickets show Details / Conversation / Update ticket as permitted. Logging a ticket separates Issue details from Visit & access.
- **Appliances:** Existing schedule, checks, reports and manager-tool sub-tabs remain unchanged.

Sub-tabs wrap to fit phones, support arrow/Home/End keyboard navigation and keep unsaved form inputs in place when switching. Validation opens the panel containing a missing required field. Selected tabs survive ordinary screen refreshes without exposing sections outside the account's existing permissions. Run `node --test www/section-navigation.test.mjs www/home-navigation.test.mjs www/ticket-archive.test.mjs` for focused checks; the isolated API/browser tests also exercise 360-pixel phone layouts, visible panel/ARIA relationships and unsaved data across tabs.

On Android, **Start sensor** reads the phone's ambient light sensor and displays illuminance in lux (lx). The app initially applies the comparison factor 1200 / 82.01 requested for this phone. This is an **unverified adjustment, not certified calibration**: raw sensor values and the applied factor are retained with each reading. Use **Calibrate** with a trusted reference meter to update the adjustment. Choose **Use live reading** to save the current adjusted value, raw value, and factor with the selected entry. If a device has no light sensor, the app reports that the sensor is unavailable; it never fabricates readings. Manually entered measurements are clearly identified as manual.

The recommended lux target defaults to **300 lx**. Each entry can keep its own measurements, notes, and photos. On Android, **Take inspection photo** opens the native camera preview, displays the live phone lux reading, and captures the photograph. When the sensor is available, that photo is saved with the exact raw and adjusted reading captured alongside it. The app creates an annotated copy showing the building, entry, capture time, recommended target, and recorded lux; it retains the original image as well. Without a light sensor, the photo is still saved without inventing a measurement. Photos and readings remain attached to their project and named entry.

Exported PDF reports contain every entry, measurement, observation, and photo in the project. **Saved reports** keeps report revisions in the app, where they can be viewed or exported as PDF later. On Android, the report is rendered locally and Android's print screen lets you save or share the PDF. In a browser, the print dialog lets you save as PDF.

Newly generated reports use a consistent, light purple PrimeOps design across lighting surveys, building checklists, individual condition records, appliance/laundry reports, combined parts schedules and account statements. Each includes a branded heading, labelled report details, relevant summary cards and clearer tables/photos. A4 print styles repeat table headings and keep photo panels together without forcing entire long checklists onto one page. Fonts and styling are embedded, so no internet connection is needed to render an export. Offline/provisional warnings, original evidence, audit permissions and calibration disclaimers remain unchanged. Previously saved HTML report revisions keep their original appearance; generate a new report to use the new design. Validate with `node --test www/report-layout.test.mjs www/appliance-report.test.mjs www/appliance-audit.test.mjs`.

In a saved report preview, use **Copy photo** under the preview to copy an embedded report photo for pasting into another document. This requires browser clipboard image support; the exported PDF itself remains a static document.

Use **Share project** to export a portable JSON package containing the editable project, entries, measurements, photos, and saved report history. The recipient chooses **Import project** and selects that package; it is added as a separate project, without replacing existing data. Project packages can contain large embedded photos, so share them using a method that supports large files. The app saves records in local IndexedDB for offline use and synchronizes signed-in users' accessible buildings to the shared backend.

## Security and data handling

### PrimeOps ownership, staff and clients

Open **`http://localhost:3001/admin/` on the server**, or through a private SSH/VPN connection. This is **PrimeOps Administration**, for the platform owner and authorised staff. **Owner** means the person who owns PrimeOps, never a customer. Client companies have their own buildings, users and records; being a client grants no platform ownership or staff permissions. The backend remains accessible even when a client's licence is missing or expired.

Administration uses a separate listener bound to `127.0.0.1` by default (`ADMIN_PORT=3001`). The public client port returns **404** for all administrator pages and `/api/license/owner` APIs, even with a platform token. Client screens contain no backend links. For remote administration, run `ssh -L 3001:127.0.0.1:3001 user@server`, then open `http://localhost:3001/admin/` on your PC. Do not publish this port, add it to the public Cloudflare tunnel, or reverse-proxy it on the client hostname. Compose binds the administrator listener inside its container but publishes it only on the host's loopback address; do not remove that host restriction.

Sign in using your platform login; no Windows app is required. The backend uses the same PrimeOps logo, typography, dark/light themes and card-based Home navigation as the client app. Choose **Add client**, enter the client name/code and main-account credentials, then **Add client & activate licence**. This creates the client, main account and first annual token in one transaction and returns to **Clients**. Click **Open account** on a client to renew licences, manage subscriptions/features, review renewal requests, or add **Buildings & checklists**. A banner identifies the open client; **Back to clients** exits its workspace. Home, Add client, PrimeOps team and Change password are platform pages, not actions for a selected client. Opening any platform page closes the client workspace. There is no global client dropdown. No separate token generator, copy/paste or activation step is needed. The backend does not expose customer ticket/report/photo content.

Inside an open account, **Licence > Account status & dates** lets platform owners and administrators manually set **Client active** and the actual licence/billing access start and end dates, in **UTC**, with a required change reason. Changes are signed and audited, preserve all client records, and reject stale edits. Inactive clients cannot sign in or use ordinary online APIs; the private platform backend remains accessible. A future start blocks access until the period begins and the device refreshes its licence. These dates govern access, not invoices or payment collection. Update installed clients to a build supporting custom-period (v2) licences before using these controls. Connected devices receive changes on their next check; a disconnected device retains its previously cached access until expiry or reconnection. Remote changes cannot instantly revoke an offline device.

The **Owner** has full platform control. Under **PrimeOps team**, the owner can add **Administrator** or **Supervisor** staff, edit those roles, reset their passwords, and deactivate/reactivate their accounts. Each person has a unique platform login; no shared owner password is necessary. Staff manage clients, licensing, subscriptions, features, buildings and checklists, but cannot list or manage platform staff, promote themselves, or modify the owner's account. Each staff member can change only their own password. Role changes, deactivation and password resets immediately invalidate that account's sessions. Staff are stored separately from client accounts and do not count toward client subscriptions. The singleton signing key remains unchanged when adding staff.

### Platform accounts, debtors and payment agreements

The private backend **Home** shows all-time income received, income received this UTC month, outstanding invoices and arrears in **ZAR**. **Accounts** shows the same platform totals and individual clients; **Open account > Account & payments** shows that client's invoices, payments and audit history. These are PrimeOps service accounts, separate from residents' rent/billing ledgers. Platform financial totals and forecasts exclude test accounts.

**Automatic monthly subscription invoices:** all companies present at the first deployment of this billing migration remain **TEST / DEMO** accounts permanently; restarting does not convert them to live billing. They show their actual tier price, monthly demonstration invoices, balances and simulated manual payments for presentations. The first demo invoice starts on deployment, not in historic forecast months. Demo invoices use a `DEMO-PO-` reference, clearly marked HTML/PDF documents and illustrative non-tax billing particulars, even when real seller/client details are not yet configured. They are never emailed or sent to Payfast, never contribute to real platform income/debt totals, and do not block access by default. Client administrators can explicitly simulate an arrears lock and clear it by simulating a full payment; this changes only TEST / DEMO account access and ledger data. Licence expiry and manually inactive status remain separate. Existing ledger records are retained.

**New clients are live billable accounts.** Registration collects the client's legal billing name/address, accounts email and VAT status, starts billing on the registration date and attempts the first invoice immediately. The full monthly fee applies without proration, then on the **1st of each UTC month**. Registration defaults to 30-day payment terms; subsequent invoices use saved terms. The server worker runs at startup and every minute, catches up missed service months after downtime and locks the company while issuing so concurrent workers/restarts do not duplicate invoices. Existing service-month invoices, including voided ones, are not recreated. Active prepaid credits are allocated automatically. Inactive clients pause processing; reactivation catches up unissued months within the configured billing start/end range. **Monthly billing & forecast** can adjust that range; live fees follow the approved tier. Missing seller/client setup or other issuance errors are logged, saved as a visible billing warning in administration/client statements and retried automatically; they never create incomplete invoices. If registration reports a billing warning, finish Invoice setup or the Debtor profile. Invoices reuse the existing PDF/download and optional email delivery flow. Invoicing does not automatically debit a card; clients still pay manually or through hosted checkout.

Owner and Supervisor roles can also issue branded **manual invoices**, with an automatic platform-wide serial (or unique custom reference), description, final VAT-inclusive rand total, issue date and due date. Blank references generate `PO-000001`-style numbers; that prefix is reserved. The form defaults the description and dates, using the client's saved payment terms. Seller details, client identity and tax calculations are snapshotted at issue: later profile changes do not rewrite old invoices. View/print/save PDF from the backend or the client's in-app statement. Legacy invoices without a snapshot remain ledger records, not newly issued tax documents. All platform roles can record manually received payments; partial payments are supported. Future-dated manual payments and overpayments are rejected. Version checks reject stale/concurrent changes. Bank reconciliation is not implemented. Manual invoices on test accounts are demonstration documents, never real payment demands.

Each client's **Debtor profile** stores legal name, registration number, explicit VAT registration status/number, billing address, accounts contact name/email/phone, payment terms and internal notes. Owner/Supervisor roles edit the profile; platform administrators can view it. The client main administrator can upload a PDF/scan, DOCX, XLSX, CSV, TXT or image under **PrimeOps statement > Your billing details**, review extracted fields and confirm/save them. Extraction is local; the original document is not uploaded or retained by the server. Ambiguous values remain for review; VAT status must be confirmed explicitly. Only reviewed structured details are saved. Clients cannot change platform payment terms or internal notes. Complete legal name, address, email and VAT status are required before issuing invoices. Payment terms never change an existing invoice's due date or grace period. Internal notes, staff identities and authorisation passwords are not included in client statements.

The Owner must first complete **Invoice setup** with the actual seller name/address/email, jurisdiction, VAT status/number/rate and payment instructions. The current template supports **South Africa only**, with full tax-invoice fields and inclusive VAT calculation rounded to cents. Non-VAT sellers issue ordinary invoices without charging VAT. Configuration and software alone cannot guarantee legal compliance: verify business particulars, VAT treatment, descriptions, dates and issuance deadlines with a qualified accountant.

**Invoice setup is saved once:** the seller particulars, each client's billing profile and the standard branded layout are reused for every invoice. Only edit these particulars when they actually change. Invoice number, dates, description, amount and live payment/balance figures vary; later profile changes do not rewrite issued identity snapshots. **Create invoice** shows missing setup beside the form with shortcuts to complete it. Submitting commits the charge and returns the updated client balance immediately, without waiting for PDF generation or email. Administration renders that returned balance directly, then refreshes platform totals. Missing details do not create an invoice. The client main administrator opens **PrimeOps statement** (independent of paid feature activation) and can select **Refresh invoices & payments**. If creation times out or is not confirmed, refresh the statement before retrying to avoid duplicate charges.

**Download PDF invoice** in administration and the client statement saves a real server-generated A4 PDF, without opening a print dialog. It includes PrimeOps branding, seller and client particulars, invoice number/dates, VAT breakdown, payment instructions, payments/credits and balance due, using the issued identity snapshot. Long instructions paginate with numbered footers. Android uses its native share/save sheet; browser/desktop downloads a PDF file. PDF generation runs locally on the server, not through an external conversion service.

Optional email requires private server environment variables `SMTP_HOST`, `SMTP_FROM`, `SMTP_PORT` (default 587), `SMTP_SECURE` (`true` for implicit TLS), and optional `SMTP_USER`/`SMTP_PASSWORD`. Issuing saves the in-app invoice and a durable **pending** delivery status together, then sends to the **snapshotted** accounts email separately, with an HTML message and the PDF invoice attached. A background worker processes pending deliveries on issue, startup and every 30 seconds; interrupted sending attempts become eligible again after two minutes. Delivery status distinguishes pending, not configured, sending, accepted and failed; SMTP acceptance is not proof of inbox delivery. Owner/Supervisor can explicitly retry a failed email. Failed deliveries are not automatically retried, and the same accepted message is not automatically sent again. An interrupted SMTP attempt can have reached the recipient before its status was saved, so recovery may send a duplicate email, never a duplicate charge.

Client administrators see their company's invoice count, outstanding balance and arrears on Home and the main Accounts & billing screen, with a link to invoices/payments/PDF downloads. These platform service charges remain separate from residents' rent accounts. While connected and visible, a lightweight revision check every two seconds picks up committed invoices/payments and refreshes the ledger; a 30-second full refresh also updates email status and date-based arrears. Refreshing preserves unsaved billing-profile inputs. A hidden or disconnected client refreshes on its next visible connected check.

**Hosted credit/debit-card checkout:** configure `PAYFAST_MERCHANT_ID`, `PAYFAST_MERCHANT_KEY`, `PAYFAST_PASSPHRASE`, explicit `PAYFAST_SANDBOX=true|false`, and `PUBLIC_APP_URL` (public HTTPS origin, without a path). Keep credentials private. Clients pay through Payfast; PrimeOps never receives card details. Expose `/api/payments/payfast/notify` on that public origin without proxy login/challenge/cache interference; never expose administration port 3001. A callback is accepted only with its ordered-form signature, configured merchant, exact checkout amount/mode, COMPLETE status, provider transaction identity and fixed-host server-to-server `VALID` confirmation. Browser return URLs never record payments. Duplicate notifications cannot duplicate receipts. Verified live payments settle the selected invoice first, then other debt; any remainder stays as prepaid credit if manual payments/voiding changed the invoice meanwhile. **Sandbox payments never add real income or settle live debt.** Real email/card delivery requires actual credentials and provider/deployment testing; do not treat local test notifications as live payment validation.

The Owner dashboard shows a rolling **12-month forecast**, overdue clients, oldest due dates and advance-paid clients. Subscription tiers supply monthly fees; billing start/end months control the invoicing range. Linked **service month** invoices replace that month's planned fee; one-off invoices remain separate. Automatic invoices link their month themselves; link manual monthly invoices to avoid double counting. Arrears are displayed separately from projected future collections. **Advance receipts** count as income once; FIFO allocations to invoices do not count as new money. Available credit offsets projected future fees. Paid-through is an estimate within the forecast horizon, not a licence extension or contractual coverage guarantee. Password-confirmed advance reversals retain receipt/allocation history and reapply other valid credit. Demo-client statements show the same calculations for presentations but do not affect platform financial totals.

Any unpaid invoice becomes arrears on the day after its due date. After **seven complete UTC calendar days** of grace, the client workspace blocks automatically: an invoice due on 1 November blocks at 00:00 UTC on 9 November if still unpaid. Every authenticated workspace request checks current debt and agreements, so no scheduler/restart is needed. Settling the overdue amount restores billing access automatically; invoices still inside grace do not cause blocking. Licence expiry and manually inactive status remain independent and cannot be bypassed by recording a payment.

The Owner or a Supervisor may grant a **dated payment-agreement extension**, entering their own current platform password and a reason. Debt and arrears remain visible. At expiry access blocks again unless overdue invoices are paid; extensions can be revoked early. The same password-confirmed roles can reverse mistaken payments or void unpaid invoices with a reason; records and audit events are retained. Administrators cannot issue/correct invoices or authorise extensions. There is no universal bypass password.

The **client main administrator** can open **PrimeOps statement** to view invoices/payments, update billing details and start card checkout. An arrears-blocked client can still sign in and use these account functions and **Check account again**, while other users see an explanation and sign-out. This exception does not bypass a separately expired licence or manually inactive client. Current web clients recheck while connected; older installed builds need updating. A disconnected device cannot learn a new server-side block until it reconnects. Once a block is known, the updated client denies cached workspace access and holds pending changes for review rather than silently uploading them.

### Client operators in the backend

Open the relevant client, then **Client operators** to create or edit client staff, including Office Administrators: display name, username, role, active status, password, assigned buildings and section/scoped-admin grants. These are client staff accounts, not PrimeOps platform staff. Students and tenants are created and managed only in the client app; the owner console and its API cannot list, create, convert or modify resident accounts or reset their passwords. Existing resident records remain unchanged. The main client administrator's role and all-client-building access remain protected.

**Set / reset client password** is available on each staff account, including the main client administrator. Enter and confirm a new password of at least 12 characters and at most 72 UTF-8 bytes; the client's old password is not required. Only the platform Owner or a Supervisor may reset a main client administrator; platform Administrators may reset other client staff passwords. Initial passwords can also be chosen when adding a client. Passwords are hashed, never returned or written to audit details. Resets preserve username, role, buildings, active status, licence and billing, invalidate existing online sessions and are audited. Stale edits are rejected. Once a password is managed in the app, backend restarts do not replace it with `ADMIN_PASSWORD`; that environment value remains the bootstrap password for unmanaged initial accounts. Offline devices cannot learn a reset until they reconnect; their locally cached offline password is updated on the next successful online sign-in.

Existing client-side account validation, user limits and ticket-reassignment safeguards apply to backend edits too. Existing sessions receive updated role/building restrictions on their next authenticated request. Backend account management remains available when billing blocks the client's workspace.

On a new installation only, use the initial client full-administrator credentials once to authorise **Set up PrimeOps administrator**, choosing separate platform credentials. Setup creates the signing key and activates the initial client's first token. Older clients without a token show **Register annual licence** once. Client administrators cannot claim an existing platform account or call platform APIs with their client sessions. Platform sessions last two hours and stay in page memory, not browser storage; refresh or sign out to discard the session. Use HTTPS for hosted deployments. There is no default platform password.

If the platform password is lost, a server operator can run `docker compose exec app node server/reset-platform-admin.cjs primeops-admin` (or `node --env-file=.env server/reset-platform-admin.cjs primeops-admin` with `DATABASE_URL` configured for direct Node). The command prompts twice with hidden input. It updates only the platform username/password and revokes existing platform sessions; signing keys, licences, client credentials and data remain unchanged. `ADMIN_EMAIL` / `ADMIN_PASSWORD` are the initial client bootstrap credentials, not a way to sign in as the PrimeOps platform administrator.

After signing in, use **Change password** to enter your current password and confirm a new password of at least 12 characters (at most 72 UTF-8 bytes). Saving signs out all platform sessions. This never changes client accounts or licences. Temporary recovery passwords should be replaced here.

One hosted app serves independent companies. Client users choose their **company code**, then sign in. Existing client records stay in their original database schema and retain their company identity. New clients start with no buildings, tickets, reports, appliance parts or checklists. The **PrimeOps Owner** Windows executable remains an optional interface to the same backend and credentials; its filename is not a client role. See [setup](owner-app/README.txt). Build it with `npm ci --prefix owner-app && npm run dist:win --prefix owner-app` only if a Windows interface is wanted.

Company business tables live in separate PostgreSQL schemas with schema-specific connection pools/search paths and no `public` fallback. JWTs are company-bound; legacy JWTs are accepted only for the original client. Offline receipt transactions use the selected company pool. New-company initialisation is transactional, starts blank, and does not seed another client's buildings/forms/parts. Browser/native storage and cached sign-ins/licences are separated by company and server; switching companies does not migrate previous-company work. Report folders use separate roots; Docker mounts `COMPANY_REPORTS_DIR` separately from original-client reports. Back up the **whole database**, `.env`/`JWT_SECRET`, reports and company-report folders.

### Company checklists

**Building checks > Create / import checklists** lets company admins/MMs build reusable question sets, choose answer types, allow photos, and assign buildings. Full company admins may choose all company buildings; MMs must select buildings within their access. Import **PDF (including scanned pages), Excel .xlsx, Word .docx, CSV/TSV, text, JSON, or JPG/PNG/WebP**. Save legacy .xls/.doc files as .xlsx/.docx first. A file creates editable checklist questions and a spreadsheet preview, preserving readable column headings, row order and cell values. Ordinary spreadsheets do not need a special header; recognised **Question/Check/Description**, **Type**, and **Photo** headings improve automatic mapping. Review OCR/extracted text before saving: fonts, pictures, merged cells and page design are not reproduced exactly. Scans use local English OCR assets, not an external document service.

JSON import accepts `title`, `questions` (`label`, `type`, `photo`), optional `sourceColumns`, and each question's matching `sourceCells`. Supported answer types: `yes-no`, `yes-no-na`, `pass-fail-na`, `text`, `textarea`, `number`, `rating`, `date`. Imported columns and values are stored with the template and snapshotted into new monthly runs; runs show the source spreadsheet alongside editable checklist answers, and exported reports retain the source table. PrimeOps Administration currently supports JSON import and manual question creation within an open client account.

Source files are limited to 25 MB; PDFs to 100 pages; generated checklists to 200 questions / 30 columns and 2 MB of saved question data. Oversized content is rejected, not silently truncated. Import previews require building selection and Save; imported building IDs are not trusted. Existing templates can be exported to JSON or archived in the company app. Archiving retains saved runs, whose question snapshots remain usable/exportable. Templates and saved work download for offline fieldwork; saving/importing templates and archiving require a connection. Existing clients keep their seeded checks in their own schema; the shared app does not bundle a client's building or form catalogue.

### Resident services and operation types

The client **Home > Features** catalogue includes **Security**, **Students / tenants & visitor registration**, **Meter checks**, **Asset management**, **Incident reporting**, and **Contractor management**. They follow the existing client request/platform approval process and are not automatically enabled for existing clients. Initial setup still allows 1-5 free features; later features retain the existing R100 once-off test fee (no payment processing).

The feature picker lists every available feature, including active ones, and shows the total available count. Its content scrolls within the screen on desktop and mobile while Close remains visible; keyboard users can focus the content region to scroll through the list.

Client administrators can uncheck active features and save to remove access immediately, without owner approval or deleting saved records. All features may be removed. Additions and reactivation still require owner approval and follow the existing activation fees. Feature changes require a connection; signed-in users receive updated permissions on their next server refresh.

Client profiles include Admin, Office Administrator, Portfolio Manager, Building Manager, Operations Manager, Maintenance Manager, Maintenance Assistant / Caretaker, Technician, and the existing Student / Tenant role. Office Administrators default to Leasing and Billing within assigned buildings, subject to approved company features. They do not gain full client-administrator privileges or user management by default; authorised administrators can select additional sections. Leasing additionally requires explicit test provisioning and server opt-in. Existing accounts keep their roles. All manager profiles, including Office Administrator, support individually selected sections and assigned buildings; only full client administrators grant scoped account-delegation rights. Portfolio and Building Managers default to all sections. Operations Managers default to operational sections and user management, excluding billing and leasing; Maintenance Managers retain their existing defaults. Full Administrators remain client-wide and are not creatable or demotable through ordinary user management.

The PrimeOps Owner, Supervisors and platform Administrators can open a client account and use **Client operators > Refresh operators > Add a client user** to create staff, select their role, assign one or more active client buildings and configure sections/delegation. Unit numbers and resident details are not requested for staff. Resident accounts are managed only in the client app and still require exactly one building and a unit number. The same validation, subscription user limits and transactional building assignment apply to staff creation from either the platform or client app. Creation is recorded in the client account audit history without passwords. The protected main Client Admin remains unchanged; platform team accounts are separate from client user profiles.

Leasing is an opt-in test workspace. Client Admins automatically have leasing permission when the company feature is assigned; Portfolio and Building Managers have it by default, subject to company activation and their individually selected sections. Other managers can receive explicit leasing permission. Linked residents can review and sign only their own leases. An explicit server allowlist and provisioned schema are required in addition to selecting the feature.

Client administrators use **Features > Client settings: residents & security** to choose **Students**, **Tenants**, or **Both** and set a security telephone number. Existing clients default to Students; accounts and building assignments remain intact. With Both, each resident account can be labelled Student or Tenant. Telephone links open the device's dialler; messages/reports are stored in-app for existing client administrators/managers, not sent by SMS/email or emergency dispatch.

- **Students / tenants** contains visitor registration. Residents see their own visits; assigned managers/admins review visits, approve/reject, then check in and check out. Check-in before approval is rejected. Residents can cancel their own pending/approved visits.
- **Security** offers Call security plus messages/reports and manager resolution statuses.
- **Meter checks** stores dated water/electricity/gas readings, units, condition notes and an optional evidence photo. History calculates consumption between readings for the same building/reference/type/unit; first readings and explicitly recorded meter resets have no consumption difference. Backdated/duplicate/future readings, unexplained decreases and changes to an existing meter's type/units are rejected.
- **Asset management** supports reviewed spreadsheet/document imports, editable per-asset inspection checklists, inspection evidence photos, condition and fault/repair/maintenance history, authorised building/location transfers, due/overdue inspection reminders and register/history reports. Tags are unique per building. Asset inspections/faults can create a linked existing maintenance ticket; duplicate tickets from the same activity are rejected, and transfers retain earlier ticket building/history.
- **Incident reporting** stores dated reports and priority with reported, investigating and resolved statuses. Residents see their own submissions.
- **Contractor management** stores contractors, trade, contact details, work start/end and scope, with active/suspended/completed statuses. It is not a contract-document/signature or payment system.

New operation screens require a live connection. Every record belongs to a building: one assigned building is preselected, multiple assigned buildings require choosing one. Ordinary users/staff cannot access records from other buildings or clients. Full client administrators retain all client buildings. MM section grants additionally restrict operation access; existing roles are reused, with no separate security login. Asset/meter operations allow maintenance assistants; contractor management is manager/admin-only. Status changes keep actor/timestamp history and reject stale edits.

Asset imports reuse the checklist document/OCR readers above, including scanned Word images when no readable text is present. Map and review the extracted building/name/tag/category before saving; up to 500 reviewed assets are saved together or none are saved. Unmapped source columns remain with each asset. Generated category-aware checklists are editable starting points, not safety certification. Up to five JPEG evidence photos per asset activity and one per meter reading are supported; uploads are resized/re-encoded to at most 1280 pixels / 500 KB per photo. Reminders are in-app, not scheduled email/push. These additions do not implement QR scanning, stock movements or a general asset warranty system.

### Leasing test workspace and existing-system imports

Leasing includes portfolio/building/unit registers, tenant codes and resident links, draft/active leases, renewals, notice/termination, occupancy, lease PDF/DOCX attachments/templates, drawn signatures with consent/version audit, expiry/arrears reminders, schedules/vacates/renovations, and PDF/Excel/lease-package exports. Billing is **simulated only**, separate from existing resident billing: manually run recurring rent/charges through a chosen date; amounts are full-month without proration. No real collection, email, certified signature or automatic monthly job is provided.

When creating or editing a lease, full administrators and users with access to multiple buildings select the building first; the unit and tenant choices are filtered to that building. The server verifies that the selected building matches the unit.

Use **Leasing > Import existing data** for another system's Excel `.xlsx`, PDF (including scanned pages), CSV or document. Choose a register and worksheet/header, map columns, correct the editable preview and explicitly confirm. Choose what the file is: building audit (unit schedule), parking audit, tenant list, lease schedule, works schedule, opening TEST balances or buildings list (main admin); import in that order. Re-importing a building or parking audit updates existing units/bays with the same number (blank cells keep current values) and adds new ones; the preview marks each row **New** or **Update existing**. Other registers never overwrite existing records, passwords are not imported, and one invalid/duplicate row rejects the entire batch. Unmapped source columns and reviewed rows are retained for the main admin's Excel audit export. PDF/OCR extraction is not guaranteed: unreadable or irregular layouts must be corrected/reviewed, not treated as verified data. Save old `.xls` workbooks as `.xlsx`.

For unit audits, tenants, leases and schedules, explicitly select the building the file belongs to from your assigned active buildings, even if only one is assigned. Every preview row shows that building. Mapped building columns must match the selection; mixed-building batches are rejected. A uniquely recognised different building in a report heading/filename is flagged for review, never used to override your selection. Leave the header row blank to detect common table headings. Unit number is the first column in building audit previews, schedules and exports. Parking audits recognise `BayNumber`, `Level`, `BayType`, `AssignedUnit`, `Status` and `Notes`; each unit shows its allocated bays from the parking audit. Unit audits recognise `UnitNumber`, `Floor`, `UnitType`, `Bedrooms`, `Bathrooms`, `ParkingBays`, `FloorArea` (square metres) and `Status`. These fields are editable and appear in each building's unit schedule and Excel export. The imported audit status is a source snapshot, displayed separately from live lease-derived occupancy; importing "Occupied" does not invent a lease or tenant.

The additive migrations are explicit and opt-in, not run by startup. See the [setup, limitations and migration checklist](Docs/leasing-migration.md). Upload the client's approved standard lease under **Leases & documents**; no legal template is invented.

### Adding client users

### Annual company licences and test renewals

Each company needs its own owner-signed annual licence. Registering a new company and main admin automatically registers and activates its first annual token. Ordinary additional user accounts share that company licence; they do not create or extend tokens. Existing licences and expiry dates are not changed on sign-in or server restart. MMs/admins see warnings at one calendar month, seven days and one day before expiry. After expiry ordinary APIs and offline sign-in lock; saved work and uploads remain. Recovery, updates and renewal stay reachable. Warnings are in-app, not background push notifications.

From **Account > System licence / renewal**, an MM/admin can **Request renewal**, including while locked by signing in on the renewal form. On the locked screen, **Activate / renew licence** opens the same dialog without requiring access to the signed-in workspace. The PrimeOps administrator approves it in **`/admin/`**. **Free test renewal** is offered only when the platform administrator enables it for that company; the server checks the flag again before issuing. It is off by default, does not affect other companies and collects **no payment**. Payment processing is deliberately not implemented or simulated.

Early renewal adds a calendar year from current expiry; late renewal starts from generation time (February 29 clamps to February 28). Issuance locks the company's licence row and requires the current token ID so duplicate/stale actions cannot add accidental years. Each device receives renewals when next connected. Offline devices cannot receive tokens remotely and must reconnect before cached expiry for uninterrupted use.

The simplified owner workflow deliberately moves signing to the hosted server: its private key is AES-256-GCM encrypted in the control database using a key derived from `JWT_SECRET`. Keep the database and that secret protected/backed up together; changing the secret without a key migration prevents signing. This is **not** the older owner-PC-only private-key design. The standalone file generator and `LICENSE_PUBLIC_KEY_FILE` remain legacy options; existing active file-signed installations must migrate deliberately rather than silently replace their key. Owner registration refuses to overwrite an active file-signed licence.

The app verifies signed licences with WebCrypto, persisted high-water time and active-session monotonic time. These controls are **not tamper-proof offline DRM** against someone controlling device code/storage or server/database backups. Use HTTPS and protected devices. Verify with `node --test server/companies.test.cjs server/access.test.cjs` using `TEST_DATABASE_URL` and optional `CHROMIUM` / `ELECTRON` paths for real browser/native UI coverage.

The app restricts executable scripts to its own origin, blocks embedded objects, and limits loaded images and connections. Imported checklist files are limited to 25 MB; survey and repair photos are limited to 12 MB each. Keep the Android device protected with its screen lock and treat exported reports and project packages as sensitive: local records are not encrypted by the app, and anyone with access to the unlocked device can open them. The backend stores workspace records and password hashes in PostgreSQL; put it behind HTTPS before allowing connections over an untrusted network.

MyBuildings integration is reserved in `www/config.js` and disabled by default. The flag alone does not enable a connection; no MyBuildings requests are made until a vendor-supported connector and authentication flow are implemented. Do not put credentials in browser configuration.

## Install and update the Android app

The GitHub Actions workflow builds and publishes an installable APK whenever changes reach `main`; it can also be started manually from the **Actions** tab. To get the newest build, open the repository's [latest release](https://github.com/harderproductions-maker/primeops/releases/latest) on the Android device, download `PrimeOps.apk`, then open the downloaded file and confirm **Update**. Leave the existing app installed; Android keeps its locally saved projects when an update installs successfully. The same APK is available as an artifact on each successful Actions run.

### In-app updates from your server

Install the first APK containing the updater manually over the existing app; older APKs cannot discover this feature by themselves. After that, Android checks the selected PrimeOps server at startup, when the app returns to the foreground, on reconnection, and every five minutes while open. Use **Check for app updates** on the sign-in screen or under **Account** to check immediately. A newer published version shows **Download and install update**. Save any open form first, allow **Install unknown apps** for PrimeOps if Android asks, and confirm **Update** in Android's installer. This is an in-place update: saved projects, cached sign-in and pending uploads are retained. Silent installation is not supported on ordinary Android devices.

The server must host the signed APK as well as the new server code; updating server files alone cannot update the app's bundled interface/native plugins. Every Android Actions build produces a **PrimeOps-Server-Update** artifact containing `manifest.json` and `PrimeOps-<versionCode>.apk`. Extract these into the server's `android-updates` folder (or the host directory set by `ANDROID_UPDATES_DIR` in Docker). For a non-Docker server, set `ANDROID_UPDATES_ROOT` to a custom absolute folder. Deploy the APK first and replace `manifest.json` last, preferably with an atomic rename. Do not edit the manifest or rename the versioned APK. The server notices new files without restarting; keep this directory when updating/rebuilding the server.

For a locally assembled Android debug build, run `npm run android:publish-update` after `./gradlew assembleDebug` in `android`. It reads Gradle's APK metadata, computes the checksum, and publishes to `android-updates`; pass a different destination after `--` if needed. Increment the Android `versionCode` for each changed APK. CI does this automatically. Publish only APKs built with the existing persistent signing key. The app verifies the exact byte count, SHA-256 checksum, package ID, higher version code and matching signing certificate before opening the installer; failed downloads can be retried. Use HTTPS for servers reachable outside a trusted local network.

The public, read-only `/api/app-updates/android` endpoint returns the latest release metadata (or `{"available":false}` before publication), `/api/app-updates/android/apk/<versionCode>` serves that version to the in-app updater, and `/api/app-updates/android/download` downloads the current release as `PrimeOps.apk`. Logged-in browser clients can open **Account > Download PrimeOps Android app** to get the APK from their selected server. The native Android app uses its verified in-app updater instead. Downloads and update checks do not require a valid account session, so an expired login cannot block installing a repair. Update checks never prevent offline sign-in or saved work. Validate with `node --test www/app-updates.test.mjs server/android-updates.test.cjs`.

Keep previously published versioned APKs in the update directory: a phone may still be displaying an earlier update notification. Its download remains valid after a newer version is published, avoiding HTTP 409 errors during an update. Each phone still checks the advertised checksum, package, certificate and version before installation. If an old APK is deliberately removed, the phone must check for updates again.

Android accepts an update only when the APK uses the same signing certificate and has a higher version code. This project uses a persistent Android debug signing key (alias `androiddebugkey`, passwords `android`) and refuses to publish if the key is missing or does not match the certificate already used by the APK. Keep a secure backup of the keystore; if it is lost, Android cannot install future builds over the existing app.

Before the first automated build, configure the repository Actions secret `ANDROID_KEYSTORE_BASE64` (**Settings → Secrets and variables → Actions**) with the base64-encoded keystore used to sign the current APK. In the build workspace, `base64 -w 0 ~/.android/debug.keystore` prints the value to save as that secret. Do not commit or publish the keystore. If the installed app was signed with a different key, Android will require a one-time uninstall before the persistent-key builds can be installed; after that migration, future updates install over the app and retain its local data.

On Android, choose **Export PDF report** to open Android's print screen, where the report can be saved as a PDF or shared. In a browser, the print dialog can save the report as PDF.

## Host the backend on your own Windows server

1. Install [Docker Desktop](https://www.docker.com/products/docker-desktop/) (free for small businesses and personal use) and set it to **Start Docker Desktop when you sign in**. Disable sleep in Windows power settings so the server stays on.
2. Copy this repository to the server, copy `.env.example` to `.env`, and set unique long values for `POSTGRES_PASSWORD`, `JWT_SECRET`, and `ADMIN_PASSWORD`. Do not keep `admin` / `admin`.
3. In the [Cloudflare Zero Trust dashboard](https://one.dash.cloudflare.com/) go to **Networks → Tunnels → Create a tunnel** (Cloudflared). Copy the tunnel token into `TUNNEL_TOKEN` in `.env`. Under **Public Hostname**, route a hostname on your domain to the service `http://app:3000`. A tunnel with a permanent address needs a domain managed by Cloudflare.
4. Start it. All containers restart automatically after a reboot:

```sh
docker compose -f docker-compose.yml -f docker-compose.selfhost.yml up -d --build
```

5. Open `https://<your hostname>/api/health`; it should return `{"status":"ok"}`.
6. Point the apps at that address: in the desktop app choose **File → Server address…**, and for Android set the Actions variable `VITE_API_BASE_URL` to it and rebuild the APK. To change the desktop default for everyone, edit `defaultServerUrl` in `desktop/main.cjs`.

Back up the database regularly with `docker compose exec database sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backup.sql`. This uses the configured database identities without renaming existing data. Cloudflare Tunnel requires no open router ports.

## Maintenance tickets and access roles

Every signed-in role can open **Account → Choose / change profile picture** to add an optional JPEG, PNG or WebP (up to 10 MB), or **Remove profile picture**. Pictures are resized to at most 256 pixels and re-encoded as JPEG before upload; the server validates JPEG content and enforces a 256 KB limit. Users can change only their own picture through the authenticated endpoint, not another account's picture. The photo appears on the Account button and in the Account dialog. Uploads/removal require a connection; the last downloaded picture stays available offline in account/server-isolated storage. Signing out clears it from the visible interface. Profile pictures are not public URLs or included in reports, tickets or other accounts' data.

Accounts are grouped into **Maintenance Managers**, **Admins**, **Students**, **Maintenance Assistants**, and **Technicians**. Assign each non-admin account to one or more buildings. Only full administrators have global building access and can configure server report storage. Managers' tickets, checks, reports and exports are restricted to their assigned buildings. Managers can manage non-manager users and billing only when all of the account's buildings are within their own assignments and the relevant section is enabled. A manager creating a new building is automatically assigned to it. Student accounts require an apartment/unit number. Maintenance assistants have OHS access for their buildings and only see maintenance tickets assigned to them. Students can log and follow their own tickets and view their own billing. Changing a resident's unit, buildings, role or active status withdraws incompatible entry permissions. Technicians only have access to appliance reports and the parts selector; they cannot access tickets, OHS, billing or user management. These restrictions are enforced by the API, not only the navigation.

Under **Users**, creating or editing an MM exposes independent checkboxes for **Maintenance tickets, Appliance reports, Billing, User management, Lighting surveys, and Building checks**, plus the existing building assignments. Existing MMs retain all their previous sections until explicitly changed; no checked sections means Home and Account only. Appliance access includes schedules, supplier quotes and (for MMs) attendance. Disabled sections cannot be fetched, exported or modified through direct APIs or offline views. Saving lighting alone preserves hidden building checks and vice versa. On permission refresh, downloaded caches/photos are cleared and pending actions are quarantined for explicit review/discard instead of uploaded under stale permissions. Disconnected devices cannot learn of revocations until reconnecting.

Only full administrators can grant **Scoped admin rights (manage MMs within selected buildings/sections)**. This requires User management and keeps the account an MM, not a global administrator. Scoped admins may create/edit ordinary MMs only with a subset of their own sections and buildings; they cannot edit themselves, full administrators, other scoped admins or wider accounts, grant scoped admin rights, or access report-storage settings. Ordinary MMs with User management retain management of compatible non-manager accounts, without gaining the ability to manage MMs. Full administrators remain unrestricted. Run `node --test www/account-access.test.mjs www/building-access.test.mjs www/offline.test.mjs www/home-navigation.test.mjs` for permission and offline regressions; the isolated API/browser test also covers permission creation/editing and section-aware workspace saves.

Use **Log a ticket**, separate from **Maintenance tickets**, to submit a building, issue title, description and category. The student's unit number is copied from their account onto the ticket, preserving the original location if the account later changes. Existing accounts without a unit must be updated under **Users** before logging a ticket. Initial categories are Electrical, Plumbing and General; managers can add comma-separated tags to a ticket pending the final tag list.

The ticket inbox shows compact, expandable conversation threads, with replies and a timestamped activity history. Updates refresh every 15 seconds while the inbox is open; unsent edits pause refresh to avoid losing text. The collapsed ticket heading shows **Assigned to Maintenance Assistant: [name]**, so the person who logged the ticket can immediately see who was assigned, even after its status changes to **In progress** or a stock/access hold. Reassignments update the displayed name and retain the original assignment in activity history. Offline users see their last downloaded assignment until reconnecting; unsynced manager edits are not visible on another device. Each ticket also shows its unit, tags, scheduled visit (or the standard 48-hour target), and recorded access permission. Students can grant or withdraw permission to enter while absent.

**Maintenance tickets** opens on **Active tickets**, showing unfinished requests only: awaiting assignment, assigned, stock/access holds and contractor work. Completing a ticket automatically removes it from Active and places it in **Archive**, without deleting the record, conversation, activity history or completion photo. Both lists show counts, refresh automatically and use the same account/building permissions as before. Downloaded tickets completed offline move to the local archive immediately with a pending-upload warning, then sync normally. Switching lists asks before discarding unsent form text. Returning from another section opens Active again.

Managers and admins can assign assistants, send work to a named contractor, or use **Set status → In progress / Awaiting stock / Awaiting access**. In-progress tickets stay in Active, retain their assigned assistant and can be completed with a photo; this status also queues and syncs offline. Assistants can only flag Out of stock or complete assigned work with a new camera photo. Managers can also close contractor work with a completion photo. Tickets cannot be marked complete without a valid JPEG.

## Technician appliance reports

Open **Appliance reports → Do checks**, choose a building and **Washer** or **Dryer**, enter the total number of that type in the laundry room, then press **Start check**. Apartment/unit is not requested or shown on appliance reports; student accounts and maintenance tickets still use it.

For each numbered machine: enter its number, tick **Working** or **Needs repair**, press **Take photo**, then **Save machine / Next**. Working machines need no fault description or part selection. Needs-repair entries show optional notes and a searchable multi-part checklist with quantities; no part is required if the fault needs diagnosis rather than a known replacement. Model defaults to the supplied Speed Queen washer/dryer model, is retained for the next entry, and can be changed under **Model**. Machine numbers need not be consecutive, but cannot repeat in the same report. Every entry needs its own fresh camera photo and location reading; there is no gallery/file upload control. Android uses the existing camera-only capture activity; browsers use a live camera preview.

Progress shows **checked / declared total**, the repair count and the number not checked. **Finish report** is available after at least one machine has been saved; machines in operation can be left unchecked. The total present is retained, and full reports explicitly state how many machines were not checked and that their condition is unassessed. Each checked machine still requires its own condition, camera photo and location evidence, and the number checked cannot exceed the declared total (up to 200 per washer/dryer report). Broken machines can be checked and included; they remain clearly flagged as needing repair. Coverage still uses the checker's declared total, rather than automatically checking against the asset register. Partial reports work offline and sync under the same validation rules. The separate requirement to submit both Washer and Dryer reports for a technician visit remains unchanged.

Each **Save machine / Next** persists the unfinished report, parts and photos locally for the signed-in account/server/role; it can be reopened offline. The current unsaved entry is not retained until Next is pressed. **Recheck** removes a saved entry so it can be captured again; **Discard unfinished report** removes only the local draft after confirmation. **Finish report** sends the entire report or queues it for automatic reconnection. While unfinished, it is visible only on this device, not to the office.

The original Speed Queen list seeds 17 parts. The supplied [price benchmark spreadsheet](./Docs/Speed_Queen_Parts_Price_Benchmark%20%281%29.xlsx) adds its OEM/alternate numbers and supplier benchmark prices: 13 spreadsheet lines, including two matched original catalogue items, produce 28 total seeded items. The deployment-safe snapshot is [server/parts-benchmark.json](./server/parts-benchmark.json); its test compares every value against the workbook. Imported prices are seeded once, preserving subsequent catalogue edits and inactive status. Prices are benchmark values, not live quotations; the source does not specify currency, VAT or quote dates.

Only **MMs and admins** receive benchmark prices from the API or see them in the catalogue/checklist. Prices are never copied into machine report snapshots, technician downloads or supplier quotation attachments. Washer checks offer only active washer parts; dryer checks offer only active dryer parts, enforced online and offline. The spreadsheet's Combo item remains in the manager catalogue but is not offered for washer/dryer checks. Its two different descriptions under OEM **205217P** remain separate lines with their original prices and need supplier confirmation before ordering.

Admins/MMs can manually add catalogue items under **Manage parts catalogue**, selecting a machine type and entering the part name. Part number is optional: leave it blank until known, then open the item and add its number using **Save part**. Name-only parts are immediately selectable for that machine type (or available on this device while queued offline) and appear as **Part number pending** in the checklist and exports. Existing unclassified custom parts must be assigned a machine type before selection. Separate unnumbered catalogue items are not combined just because their names match. Catalogue changes affect new checks; historical report snapshots remain unchanged and parts exports warn when numbers still need confirmation before ordering.

### Machine asset management

The **Machine assets** tab tracks physical machines by building, washer/dryer type, machine number and serial. Technicians must enter the serial on the first check; later checks fill it automatically and lock it against accidental changes. Each serial is unique, including retired records. Numeric machine labels such as `01` and `1` identify the same position. To install a different machine at that position, tick **Replace machine**, enter its new serial and finish the check. The previous asset is retired, not overwritten, retaining its checks and parts history. A changed serial without explicit replacement is rejected, including conflicting offline uploads.

Breakdowns count separate **Needs repair** episodes in check-time order. Repeated broken checks count once until a **Working** check closes the episode. Retired and replacement machines have independent histories. The dashboard ranks assigned buildings by total breakdowns, shows current repair counts, per-machine inspection histories and frequently requested/ordered/replaced parts. Historical checks without a serial-linked asset are explicitly counted as unlinked and excluded from machine breakdown totals; they are not silently attributed to a replacement machine.

Requested quantities come from saved checks. **MMs/admins** explicitly mark requested parts **ordered**; **technicians or managers** confirm ordered quantities **fitted/replaced**. Orders cannot exceed their request and replacements cannot exceed ordered quantities. Each action records its actor, quantity and server date in an append-only audit trail. Separate checks can request the same part again, so review outstanding requests before ordering. Retried actions reuse their operation ID to avoid double-recording after a lost response. Part actions require a connection; machine checks, serial reuse and asset snapshots work offline and pending totals are provisional. A machine registered only in pending offline work must sync before it can itself be replaced.

MMs/admins can **Download Excel report**: a genuine `.xlsx` workbook, not CSV, with a ranked building summary and a separate named worksheet for every accessible building, including buildings with no registered machines. Each building sheet contains active/retired serials, breakdown counts, part frequencies, request reconciliation, inspection history and the dated order/replacement audit trail. Serial and part numbers remain text, preserving leading zeros. Android opens the native save/share sheet; browsers and desktop download the workbook. Workbook creation requires a connection. Building access and export permissions are checked by the server.

Validation: `node --test www/laundry.test.mjs www/machine-assets.test.mjs www/offline.test.mjs server/parts-catalogue.test.cjs server/machine-workbook.test.cjs`. Set an isolated `TEST_DATABASE_URL` and run `node --test server/access.test.cjs server/machine-assets.test.cjs` for API/database checks.

Saved reports retain a snapshot of each machine's selected part details, so editing or disabling a catalogue part never changes an earlier report. Technicians see only reports they created in their currently assigned buildings; managers see all reports in their assigned buildings, and administrators see all appliance reports. Technicians can export their full reports. Managers/admins can choose **Full report** or **Replacement parts report** for one or multiple selected reports (up to 200). Full exports include each machine's number, model, condition, camera evidence, notes and parts. Replacement-parts exports combine quantities by part number and description, showing each building, machine number, model, report reference and quantity. Different historical descriptions for the same number remain separate for review. Selection is manual; these exports do not mark parts as ordered or prevent a later re-export. Historical single-appliance reports remain readable; their old apartment/unit values remain stored but are no longer displayed/exported.

Exports use the Android PDF workflow or the desktop/browser print dialog. Downloaded/pending reports can be exported offline by managers/admins; offline combined exports are marked provisional.

#### Supplier quotation requests

MMs and administrators can open **Appliance reports → Supplier quotes**. Under **Building email and suppliers**, choose a building, enter its quotation-reply email, add supplier names/emails, and save. MMs can view/change contacts only for their assigned buildings; technicians, assistants and students cannot access supplier contacts through the UI or API. Changing contacts requires a server connection. Open this tab online once to download its contacts for offline preparation.

Select the saved appliance reports whose parts are still needed, then choose **Prepare requests per building**. The app combines quantities by part number/description separately for each building, retaining machine/model/report references. It never combines different buildings in one request. Reports from offline/pending work are explicitly marked provisional. Selection is manual: previously requested or replaced parts are not automatically excluded, and no purchase order or delivery tracking is created.

Each listed supplier gets a **separate email**, with that supplier in **Bcc** and the building email as the visible **To** recipient. No supplier's address or quote is shared with another supplier. The request asks the supplier to quote directly to the building email, including unit prices, VAT, availability, delivery charges and lead times. Opening the composer does not send anything: MM reviews Bcc/recipients/attachment and presses **Send** in the device's email app.

On Android, **Open email app** prepares the recipient, Bcc, subject, item list and an attached self-contained HTML replacement-parts report. Android's generic email intent cannot force a Reply-To header; the building destination is stated prominently in the body and visible To field, so suppliers should send quotes directly there rather than simply replying to the sender. Email apps may handle prepared fields differently; verify them before sending.

In browsers/desktop, **Open email app** uses the default mail handler; attach the report manually using **Download parts report** or **Save / print PDF**. Alternatively, **Download email draft with report** creates a UTF-8 `.eml` draft with the report already attached, the building as **Reply-To**, and exactly one supplier in Bcc. Open it in an email client that supports editable drafts; clients that open `.eml` read-only can use the normal composer and manual attachment instead. No SMTP account is required on the app server.

The app cannot confirm delivery, control supplier replies, collect quotes into the app, or change the device email account's From address. Offline preparation uses downloaded contacts; the email app determines when a queued email is actually sent. Already-exported requests are external documents and do not update when contact settings or building access changes.

Run `node --test www/parts-quotes.test.mjs` for per-building grouping, Bcc isolation, reply routing, attachment content and offline contact scoping. The isolated API/browser tests also cover contact edits and request preparation by MM.

#### Appliance check audit

Press **Start check** at the laundry room. The app requires a fresh location at start, with each machine photo, and at report completion; denied, unavailable or stale locations block completion. Android requests foreground location permission only and rejects locations identified by Android as mock-provider readings. Browser camera/location capture requires HTTPS (or localhost); accuracy and availability vary by device, especially indoors and on desktops.

Admins and maintenance managers alone see report/per-machine coordinates, accuracy, UTC device times, elapsed seconds and the server's receipt time in saved reports and full exports. Technician API responses, lists and full exports omit these audits and photo capture timestamps. Reports predating this feature are marked as having no location audit; new submissions require it. The report and machine audits are immutable after submission.

Finished offline checks retain captured evidence in the account's existing local outbox and show **Pending server receipt** until uploaded. Offline completion, delayed uploads (over 5 minutes), future device times and elapsed/clock discrepancies are flagged for manager review, not silently treated as verified. Reopening a draft preserves recorded elapsed time but excludes time while closed; clock discrepancies may therefore need review. Receipt confirms storage on the server, not that the location or work is authentic. Device clocks/GPS/camera metadata can be manipulated and browser mock locations cannot be detected reliably; this is supporting evidence, not tamper-proof proof of attendance or completed work. Previously queued reports without a technician visit are retained but cannot bypass the new visit rules: review/discard a blocked item and capture new work under a current visit.

#### Technician bookings, building GPS and attendance

Open **Appliance reports** from Home. Sub-tabs separate **Schedules / Bookings**, **Do checks**, and **Saved reports**. Admins and MMs also have **Supplier quotes**, **Parts catalogue** and **Building GPS**; only MMs have **Attendance**. One panel is visible at a time. Switching tabs preserves the open check form, captured machine evidence and report selections without refetching; saved drafts reopen under **Do checks**. Sub-tabs wrap on phones and support arrow, Home and End keys.

**Schedules / Bookings** opens a clickable month calendar. Tap a booking directly to open its details and large, picture-labelled actions in one focused dialog. Tapping a date opens that day's booking (or a short chooser for multiple bookings); **more** shows the full day. Only the current action's fields appear; **Back to booking** returns within the same dialog, without page navigation. Previous, Next and Today stay available; month/building/technician filters and cancelled/rescheduled history are tucked under **Filter calendar / show history**. Whole-day appointments use their actual SAST day and exclusive end time. Technicians only see permitted bookings and can open checks or request changes. Calendar browsing and details work from downloaded schedules offline; changes require a connection.

Booking screens use short labels and one-line save confirmations, not repeated instructions or extra confirmation popups. Optional details are collapsed. Failed saves, conflicts, offline status and pending MM approval remain explicit.

Admins and MMs use **New booking** or **Book this day**; the booking form opens in the same dialog, prefilled for the selected date and filters. Saving closes it and selects the booked date with a success message. Administrators may manage all buildings; MMs only their assigned buildings. Book an active assigned technician for a whole day or a start/end time, using **Africa/Johannesburg** (SAST). Overlapping bookings are rejected without changing the original. In **Building GPS**, set a pin at each building's laundry area first, using coordinates or **Use my current location**. The default radius is 100 metres (configurable from 20 to 500).

On startup the server fills missing pins for 15 catalogue entries using a **100 m radius**. Sources and coordinates are recorded in [building-locations.cjs](server/building-locations.cjs); existing pins are never overwritten, and inactive/unrecognised properties are not changed. These are public building map pins, not surveyed laundry-room positions; managers can refine them in **Building GPS** if an on-site check shows a mismatch. Hluma is in Durban; Varsity Studios is in Pretoria. The user confirmed **Braamfontein Project / Central Studios** is the same building as **Crescent Studios**, so both entries share its pin. **Richmond Central** uses neighbouring **The Richmond**'s sourced pin at 42 Richmond Avenue at the user's request to use the closest available match; confirm this approximate boundary on site. Existing Apex pins remain unchanged. Run `node --test server/building-locations.test.cjs` to validate seed data and non-overwriting behavior.

Technicians select a booking before starting. Start, each machine's evidence, and report completion must all be inside that building's boundary and booking window. GPS accuracy must be at most 50 metres and at most half the boundary radius; distance plus the reported accuracy must fit inside the boundary. Missing pins, poor/unavailable GPS, mock-provider readings and wrong-building evidence block checks. The API independently validates the same rules; changing the building dropdown or sending requests directly does not bypass them. Managers/admins retain their existing ability to create appliance reports without technician check-ins.

**Both Washer and Dryer reports must be received successfully for a visit before the technician can move to another visit.** A technician can choose **Extra visit** at any assigned building with a configured GPS pin; this creates a same-day visit and notifies the relevant MMs. An unfinished active visit must first be completed, cancelled by a manager (current bookings or extra visits), or rebooked by MM when overdue. Booking cancellation is retained in history; overdue booked appointments cannot be cancelled to erase misses.

Downloaded bookings and boundaries work offline. Check-ins and reports are saved in order and validated again against current server permissions, booking windows, cancellations and GPS pins on sync. Pending checks are visibly provisional: moving to another visit requires sync confirmation. Offline evidence completed inside its original window may upload later, so attendance totals can change when delayed work arrives. A disconnected phone cannot learn about changed/cancelled bookings until it reconnects. Old drafts without a valid visit can be explicitly discarded without deleting already submitted reports.

MMs/admins select a booking and choose **Change**, **Cancel booking**, **Postpone** or (when eligible) **Mark as missed**, all in the same dialog. **Change** chooses a new day/time or whole day; the technician/building stay fixed. **Postpone** offers **Choose a later date now**, or **Leave until rescheduled** with a required reason. An undated postponement releases the old slot, is excluded from automatic missed-attendance totals, and stays in **Awaiting reschedule** until a new date is chosen or it is cancelled. Its original time, reason, author and timestamp remain stored. Choosing a replacement checks conflicts atomically, links the new booking and retains history; failed saves leave the original/postponement unchanged. Undated postponed bookings can be rescheduled even after their old date passes. Ordinary overdue appointments use **Rebook visit**. Started visits/evidence cannot be postponed or moved. Cancellation has an inline confirmation rather than an extra popup.

Technicians select a booking and choose **Request change**, **Request cancellation** or **Request postponement**, with a required reason. Change/postponement requests both go to MM for rescheduling; they do not directly release the appointment. **Pending MM approval** appears on the booking, while the original stays active. Managers can review from that booking or **Pending change requests**: approve cancellation, decline, or **Choose new time & approve**. MM chooses the replacement date/time; saving approves the request atomically. Requests/decisions stay scoped to the technician and authorised building managers. Only one may be pending per booking. Submission/review requires a connection and is not queued offline; downloaded requests are informational.

Only **maintenance managers** can access attendance alerts or the full attendance report, including through the API; admins, technicians, students and assistants cannot fetch that endpoint. MMs receive an in-app popup for new extra visits and unrebooked overdue bookings: no received reports means **missed**, and one required report missing means **incomplete**. Alerts refresh on sign-in, foreground/reconnect and every minute while the app is visible. These are in-app alerts, not background Android push notifications or continuous location tracking. Server outages prevent alert refresh.

**MMs and admins** can choose **Mark as missed** on an eligible booking: its technician/date/visit are already selected, so only a required note and Save remain. **Schedules / Bookings → Did not report to work** still offers a specific visit or whole workday. A whole-day entry records one linked entry per assigned/booked building, even without a booking there. MMs must have access to **every** affected building; otherwise an admin must record the whole day. Future bookings, cancelled/postponed visits, duplicate records and visits/days with received check-in/report evidence are rejected. Recording requires a connection and is not queued offline.

Manual no-show records show on the manager/admin calendar and selected-day agenda, with the note, author and recording time. They are never exposed to technicians, students or assistants by the schedule API or downloaded projections. MMs see only their buildings' entries, including the permitted part of an admin-recorded whole-day absence. Existing cached notes are scoped to the account/server and building permissions. The full **MM-only** attendance export includes these records separately from automatic missed/incomplete totals. Recording does not cancel visits, erase check evidence or disable later check-ins/uploads; a later offline submission may contradict a manager's entry, so review both histories. These entries are retained, not silently overwritten or deleted.

Under **Attendance → Missed visits and attendance report**, MMs can select dates and optionally a technician, then download/print a report showing missed technician-days, missed appointments, incomplete appointments and required Washer/Dryer checks not completed. Extra visits are listed but not counted as missed bookings. Days are distinct technician/date pairs in SAST, so several missed appointments by one technician on one day count as one missed day. **Rebook visit** links the replacement without deleting the original missed/incomplete record or its attendance history; the original alert stops once rebooked.

Run `node --test www/technician-visits.test.mjs www/offline.test.mjs` for schedule, GPS and offline rules. The isolated API/browser test below covers booking permissions, overlap rejection, both-check completion, missed/incomplete attendance, rebooking history and MM form submission.

Developer validation: run `npm run check` and `npm run build`. With a PostgreSQL connection that permits creating temporary databases, run `TEST_DATABASE_URL=postgres://... node --test server/access.test.cjs`. The test creates and removes its own isolated database and does not change application data. Optionally set `CHROMIUM` to an installed Chromium executable to check the visible navigation, separate ticket screens and appliance forms for each role in a headless browser.

## Offline phone use

Install the current APK and sign in while connected at least once. Leave the app open until the offline copy is ready. Buildings, tickets, parts, appliance reports and (for permitted roles) users and billing accounts are downloaded to this device. First-time sign-in and data never downloaded to this phone require a connection. The installed Android app bundles its interface; an ordinary browser page must first load from the server and is not an installable offline website.

After a successful online username/password sign-in with this version, the same account can sign in again on this device while the server is unreachable, even after signing out. Use the same server address, username and last password verified on this device. Each account/server has its own salted password verifier; your sign-in password is not saved in plain text. Network failures, timeouts and server errors allow offline access, but an online authentication rejection does not. Accounts used only with an older version must sign in online once after updating to enable this feature. OHS access also requires that account's workspace to have been downloaded. Offline access uses the last verified permissions; password changes, disabled accounts and permission changes cannot be checked until the server returns. Expired server tokens require online sign-in before syncing.

While disconnected, continue OHS work, log tickets without access permission, reply to downloaded tickets, record status changes and capture completion photos. Technicians can select downloaded parts, save appliance reports and export them locally. Managers can also queue users, billing transactions/statuses, parts and buildings. Save/submit the form before leaving its screen; unfinished form fields are not automatically saved. Downloaded billing is dated and provisional; a queued payment is not an online payment or proof that funds were received.

The banner shows pending uploads. Changes are saved in IndexedDB, separately for each account and server, and survive closing/reopening the app. Reconnection (or **Sync now**) uploads changes in order while the app is open. Android does not guarantee uploads after the app is closed; reopen it with connectivity to finish syncing. New local IDs are replaced with server IDs as uploads are confirmed. OHS revisions that conflict with another device require explicit review rather than silently replacing server work. Server report copies from offline exports are queued as well.

**Pending changes** shows rejected or conflicting actions. They remain on the device until retried or explicitly discarded. Discarding an action also discards later queued actions because they may depend on it; it does not undo actions already uploaded. After discarding, reload the current data and resubmit corrected work. Stale account/part/status changes are rejected for review, not silently applied. The backend checks the user's current permissions and uses durable operation receipts to prevent duplicate tickets, charges or reports when an upload is retried.

Apartment access grants and withdrawals are **online-only**, including granting access when creating a ticket. Do not rely on cached access permission before entering an apartment: the resident may have withdrawn it since the last download. Offline tickets can be submitted without granting access, then permission can be recorded once connected.

Keep the phone locked. Cached account/billing information, photos and queued manager-entered passwords are stored locally without application-level encryption. Signing out hides them from other app accounts but does not delete unsent work. Clearing app storage or uninstalling deletes unsynced work. An expired login must be renewed before uploads can resume.

When verified roles or building assignments change, the app removes downloaded API data/photos, re-scopes and saves the OHS workspace, and blocks existing pending actions rather than uploading them with changed permissions. Discard these blocked actions and re-enter permitted work. Laundry drafts are scoped to the current account, server and permissions; drafts from older permission sets are not reopened. A disconnected phone cannot learn about revoked access until it reconnects. Reports already downloaded or sent outside the app cannot be remotely revoked.

Run `node --test www/offline-auth.test.mjs www/offline.test.mjs` for offline sign-in and queue/projection checks. The optional Chromium checks above also cover disconnecting the API, saving an appliance report, reopening it offline, and uploading it exactly once after reconnecting.

## Building checks and repairs

From the **Home** dashboard, open **Building checks**, select a property, and choose one of the 21 supplied monthly forms. The question labels and field types are extracted from the completed PDFs in `Docs/`, but their historical answers are not copied into new runs. Use `npm run forms:extract` to regenerate `www/building-check-templates.json` after updating those source forms. Fill in the answers, add photos where prompted, and submit. Each property/form/month has one saved run and submitted PDF revisions; the previous months remain unchanged. Draft answers and photos are saved locally.

Use **Import completed checklist** only for an existing CSV, Excel, or PDF inspection record. Select its inspection date and target property; the app does not retain the imported PDF itself. Spreadsheet imports must include a **Check**, **Item**, **Name**, or **Inspection Item** column.

Use **Next month** on a run to create a blank copy of that form for the next month. The current run is never overwritten. Each answer or photo change records the entered editor name and timestamp; old history without actor data is shown as **Not recorded**. Editor names are manually entered and are not verified against the signed-in account. Submitted reports remain available from the monthly run. Older free-form/imported checklists remain under **Existing checklists** for their property. Records for buildings assigned to the signed-in user sync to the shared workspace and remain available offline on this device.

## Install and test the shared backend

The shared backend serves both the web app and its JSON API. Install Docker with the Compose plugin, then from the repository root:

```sh
cp .env.example .env
```

Edit `.env` and set unique, long values for `POSTGRES_PASSWORD`, `JWT_SECRET`, and `ADMIN_PASSWORD`. For example, generate `POSTGRES_PASSWORD` and `JWT_SECRET` with `openssl rand -hex 32`; choose a unique administrator email and password. Keep `.env` private; it is ignored by Git. When publishing behind a TLS-terminating reverse proxy, add the public origin (for example, `https://surveys.example.com`) to `CORS_ORIGINS`.

Start the database and app:

```sh
docker compose up --build -d
docker compose ps
curl http://localhost:3000/api/health
```

The health endpoint should return `{"status":"ok"}`. Open [http://localhost:3000](http://localhost:3000) and sign in with `ADMIN_EMAIL` and `ADMIN_PASSWORD`. The first startup creates the administrator and building catalog. From **Account**, an administrator can add accounts and assign buildings. Use `docker compose logs -f app` to inspect startup and server errors. `docker compose down` stops the services while preserving PostgreSQL data; `docker compose down -v` also deletes that database volume.

To use the installed Android app with this backend, make the backend reachable over HTTPS and set the repository Actions variable `VITE_API_BASE_URL` to that HTTPS origin (**Settings → Secrets and variables → Actions → Variables**) before running the Android build workflow. The workflow embeds this URL in the APK. If building locally instead:

```sh
VITE_API_BASE_URL=https://surveys.example.com npm run build
npx cap sync android
```

Install the resulting APK from the workflow artifact or release. Leave `VITE_API_BASE_URL` unset for a same-origin web deployment, where the backend also serves the web app. The default APK does not contain a public server address; its API requests use the app's current origin.
